## 1) Spec recap (catalogue, verbatim key lines)

From CAT lines 385–391:

> **N43 · Forward-Proof Fact Cards.** Shareable cards with status, an as-of date, the source and a check code that shows whether the card is out of date.
> - **What the user does:** shares a card to a group chat. Weeks later, anyone who opens the code sees "Status changed on Dec 1".
> - **Why it's distinctive:** designed for forwarding chains that strip out context.
> - **Grounding:** https://frontlinetech.km4s.ca/?p=329, and the earlier disagreement-card and as-of history ideas.
> - **Tonight:** HTML-to-PNG cards and a /check page (2 h).
> - **Main risk:** needs a lasting backend, images can be faked, and forwarding strips alt text. No tracking parameters. Simplest form: an as-of date plus a short link.
> - Feasibility 4 · Brief fit 4 · Survives scrutiny 3

Context lines:
- CAT 1182, combination C: "N46 status strip reused on N122 Lobby Poster, N43 forward-proof cards and the N38 SMS simulator". CAT 1183 adds: "one reviewed issue record renders to web, print and SMS, so every channel carries the same status, date and source."
- CAT 1189: N43 is listed among ideas that "partly overlap the previous model's list". They are "flagged in their entries rather than dropped".
- CAT 615 (N68, a sibling idea): "Every field needs an evidence pointer, an as-of date and an expiry."

The idea in one sentence: a card that can be forwarded, whose small code lets anyone ask Muni later whether the card still matches the record. N43 does **not** make Muni a source of truth about status. It only reports whether Muni's own checked statement still matches the sources Muni cited.

## 3) Proposed data records for Muni

These are new records. They reuse the existing `Snapshot`, `Passage`, `Claim` and `Discrepancy` models (`pipeline/models.py`) and add two small models, `Card` and `CardCheck`.

### 3.1 Check-code scheme (proposal)

```
canon   = JSON of {v, matter_id, claims:[{id, text_sha256,
             cites:[{passage_id, snapshot_sha256, passage_sha256}]}]}
          with keys sorted, no whitespace (separators "," ":"), UTF-8, claims sorted by id, cites sorted by passage_id
norm(t) = NFKC, then collapse every run of whitespace to one space, then trim
text_sha256    = sha256(norm(card sentence as shown))
passage_sha256 = sha256(norm(passage.text))          # the cited words, not the page
snapshot_sha256 = Snapshot.sha256 the reviewer checked (= Claim.checked_against[snapshot_id])
card_sha256 = sha256(canon)
check code  = first 8 hex of card_sha256, shown as xxxx-xxxx (e.g. a4cb-7916)
short link  = muni.<host>/c/a4cb7916     # static file site/data/cards/a4cb7916.json
```

Design choices and why:
- **The code is content-addressed, not random, and has no dates in it.** Everyone who shares the same card shares the same code, so the link carries nothing about who shared it. That meets "No tracking parameters" (CAT 390). Re-issuing an unchanged card gives the same code. Dates live in the registry record (issued_on and the check history), not in the hash.
- **The code includes both the snapshot hash and the passage hash.** The snapshot hash pins the exact file the reviewer read (PLAN §3 line 89). The passage hash lets the staleness check follow PLAN §6.9: when a page's bytes change, compare the cited passage before sending anything back to review. This matters because page bytes change without any change in content. F17 showed that the same P202 page hashes differently under Chromium and plain GET. A bytes-only check would mark every card stale whenever the fetch method or a page menu changes.
- **Whitespace is normalised.** F19's sentence breaks across a line in the PDF text layer. Without normalisation, the same words would hash differently.
- **8 hex = 32 bits.** That is enough for a lookup key in a registry of a few thousand cards, but not unique by itself. The build must fail on any 8-hex collision and widen that card's code to 10 hex. The /check page always shows the full card text and the full 64-hex `card_sha256`, so a viewer can compare what they hold with what Muni issued.
- **The code is a fingerprint, not a signature.** Anyone can compute it, so it does not prove that an image came from Muni. Authenticity comes only from opening the link on Muni's own domain and comparing the text (see §5).

### 3.5 State rules (pipeline, deterministic, no AI)

| State | Rule | Card banner |
|---|---|---|
| `current` | Every source was re-fetched within its window (F8: agendas daily in a cycle, guidance weekly). Bytes are the same, or the bytes changed but `passage_same` is true for every verbatim cite. No newer reviewed event. Card not withdrawn. | "Still matches the records Muni checked on {latest_fetched_at}." |
| `source_changed` | Any verbatim cite has `passage_same: false` or the passage is gone. Or bytes changed on a `research_note` cite (it can't be text-matched, so a person must recheck). This raises a `source_drift` Discrepancy (`checked_sha256`, `latest_sha256`) and sets the Claim to `needs_recheck` (F6). | "The source changed after this card was made. Muni is rechecking. Don't rely on this card." |
| `superseded` | A newer **reviewed** Event exists on the matter (for example a notice of passing or a withdrawal). | "Status changed: {event.kind in plain words}, dated {event.date} in the record." It links to the new record. The record date is the event's date, never the date Muni noticed. |
| `not_rechecked` | Any source is blocked, sign-in or dead, or has not been re-fetched within its window. This includes the site's own last build being older than the window, which the page computes in the browser from `run_on`. | "Muni can't confirm this card is current. Last checked {date}." |
| `withdrawn` | Muni retracted or corrected the card (error ledger). | "Muni withdrew this card on {date}: {reason}." |

A dated window inside the card (C-h5) also shows "closed" or "open" in the browser from `deadline_date`, as Windows Wall already does. A closed window does **not** make the card stale. It makes the line historical.

## 4) UX outline

**A. Card (PNG plus a copyable text block)**
- Content: matter title, status line, 1–3 claim sentences each with a text provenance tag, "As of {date}", source publisher and short title, `muni…/c/xxxx-xxxx`, and the footer "Muni is independent and is not the official notice."
- Everything essential is in the pixels and in a plain-text version shared alongside, because forwarding strips alt text (CAT 390). Status is shown in words as well as colour. There is no QR-only path: the code is printed as text.
- What it does NOT establish: that the status is current on the day someone reads it, that Muni is the official notice, that the person who shared it agrees with anything, or that the claim applies to the reader.

**B. Share sheet (on a matter page)**
- Choose the claims, preview the card, then "Copy text", "Save image" or "Copy link". Only `approved` claims can be selected. Claims in `needs_recheck` or with a `not_checked` or `source_unavailable` window are greyed out with the reason.
- Empty state: "Nothing on this matter can be made into a card yet. It hasn't been checked against a stored source." This is today's state for every matter (F14).
- What it does NOT establish: that the selected lines are the whole story. The card says "{n} of {m} facts. Full page: link."

**C. /check page (`/c/<code>` or a form where people type the code)**
- It shows the frozen card text exactly as issued, the full 64-hex `card_sha256`, then the current state banner (§3.5), then a "What changed" list (per source: checked hash vs latest hash, passage same or changed, re-fetch date) and links to the official records.
- It asks the viewer to "Compare this text with the image you received. If they differ, the image was altered."
- States:
  - **Current**: green plus the words.
  - **Source changed**: amber, with "rechecking".
  - **Superseded**: "Status changed on {record date}". This is the catalogue's "Status changed on Dec 1" example, worded with the date from the record.
  - **Not rechecked / unknown**: grey, "can't confirm".
  - **Withdrawn**.
  - **Code not found**: "No Muni card has this code. Check the spelling. A missing code doesn't mean the card's claims are false, only that Muni didn't issue it."
  - **Offline / data failed to load**: "Can't check right now", never a default to "current".
- What it does NOT establish: which source is right when they differ (F7, F30), that nothing happened if no new record was found (F31), that an unlisted decision doesn't exist (F23), or any legal effect. For example, it can't say the 15 King by-law is in force (F24).

**D. Staff view (inside the existing Staff/Drift page)**
- A table of issued cards by state, with the `source_drift` Discrepancies that changed them and a "recheck" link to the review file. This reuses Drift Sentinel output and adds no new workflow.
- What it does NOT establish: which cards are still circulating. Muni doesn't track shares.

## 5) Risks and what must not be claimed

1. **Never claim "this is current" beyond the last re-fetch.** The strongest honest wording is "matches the records Muni checked on {date}" (F4, F5, F29). Whenever freshness can't be shown, the default is `not_rechecked`, never `current`.
2. **The code is not authentication.** Images can be faked (CAT 390), and a sha256 prefix that anyone can compute proves nothing about who made the image. Only the /check page on Muni's domain, showing the frozen text, lets someone detect tampering. Don't call it "verified", "signed" or "tamper-proof".
3. **Byte hashes give false alarms.** The same URL gave 841,978 B and 58,483 B with different hashes depending on fetch method (F17). HTML locators drift (F28). Use passage-level comparison for verbatim cites. Treat `research_note` cites as "a person must recheck" on any byte change. Today 11 of 17 passages are research notes (F14), so most current claims could only ever reach `source_changed`, never an automatic `current` after a page edit.
4. **"Status changed on {date}" must use the record's date.** Don't use the detection date or a meeting date (SKILL line 494: "A meeting date is not automatically a participation deadline"). If the record gives no date, say "found on {fetch date}; record undated" (F26).
5. **Absence isn't evidence of no change.** The heritage page not listing a notice of passing for 131 William (F23) cannot become a card that says "not designated". It can only say "No designation by-law was found in the records checked" with the check date (C-h4).
6. **No lasting backend is needed. The real cost is a lasting rebuild.** The registry is static JSON, consistent with PLAN §1 ("No server runs at request time"). But if the pipeline stops running, every card must decay to `not_rechecked` through the browser-side age check. Muni must not promise cards will be checked "forever".
7. **Data gaps block it today.** 0 snapshots have hashes, 0 claims have `checked_against`, and the new source-drift check compares bytes only, without the passage diff (F13, F14). With no `checked_against` values it currently flags nothing, three snapshot URLs are the bare site root (F36), and S-dec8-packet's `ok` conflicts with a logged 403 (F37). No card should be issued from those snapshots until they are fixed.
8. **No tracking.** No per-share ids, no UTM parameters and no analytics on `/c/`. The content-addressed code makes this structural.
9. **No personal details.** Cards must not reproduce staff contact lines from notices (the 15 King notice has named staff contacts) or anything from correspondence passages (PLAN §5 line 141).
10. **Don't present the precedent as evidence.** The frontlinetech page (F34) and the "earlier disagreement-card and as-of history ideas" (F35) were not read. The only verified precedent for change detection is the guide's own "page-hash monitor" recommendation (F27, Reported).
11. **Partial cards.** A card that drops a condition breaks Qualifier Keeper. Cards may only reuse approved claims as they are, never shortened text. For example, C-k4 "only if no appeal is filed" must travel with any 15 King status line.
